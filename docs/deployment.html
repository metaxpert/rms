Two ways to adopt it

This is the one decision to make up front. The good news: both run the same software. The difference is only which modules are switched on for your company.
Path Ano ERP yet

Standalone RMS

Your situation
You just want a restaurant system. You don't run the MetaXperts ERP for anything else.
What you do
Install fresh, then create a company with only Restaurant (plus Inventory, Finance & CRM) switched on.
Effort
A full install — roughly six commands, once.
Result
A server that behaves like a dedicated restaurant product. Every unrelated screen is simply hidden for that company.
Path BERP already running

Add to an existing ERP

Your situation
You already run the MetaXperts ERP for accounting, inventory, sales — and want to add the restaurant.
What you do
Keep your deployment, update to a build that has the restaurant module, then switch the Restaurant feature on for your company.
Effort
An upgrade plus a feature toggle. No new server.
Result
A Restaurant section appears beside your existing modules and shares your customers, inventory & books.
🔀

Standalone and integrated are the same build. Which modules a company sees is a setting in the database, not a different download. A company with only Restaurant on is a standalone RMS; the same company with HR, Purchasing and Sales added is an integrated one. You can start standalone and light up more later — no redeploy, no migration.

What a standalone install looks like

Done once, on the server, inside the MetaXperts ERP repository. This is the whole thing — annotated so you can see there's no hidden complexity.

Get the code & set your secrets

Clone the ERP repo and replace the three placeholder security keys with your own random values. This is the one step you must not skip before real customers.

# three secrets that protect logins and internal calls
JWT_ACCESS_SECRET=$(openssl rand -hex 32)
JWT_REFRESH_SECRET=$(openssl rand -hex 32)
SERVICE_AUTH_SECRET=$(openssl rand -hex 32)

Start the whole stack

One command brings up the database, broker, cache, storage, the API, the web console, the AI service and monitoring. The accounting workers are already on in this mode.

docker compose -f infra/docker-compose.prod.yml up -d --build

Create the database tables

The stack is up but empty. This builds the schema — safe and idempotent, it only creates what's missing.

bash infra/scripts/migrate-prod.sh
# confirm it's healthy:
curl -s http://127.0.0.1:3300/health/ready   # → ok

Create your restaurant company

Provision a company and switch on the restaurant feature bundle. That last loop is what makes it a standalone RMS — everything else stays hidden.

# enable Restaurant and the modules it needs
for f in inventory finance crm restaurant; do
  PATCH /tenants/<id>/features/$f  { "enabled": true }
done

Put it behind HTTPS

Point your domain at the server; the included Nginx config serves the console and proxies the API. Now staff open https://rms.yourdomain.com and the apps point at …/api.

Load your menu & go

Set up your accounts, ingredients, menu, floor and recipes (next section), then open for service.

💡

Want to see it working before doing it for real? A one-command demo seed builds a fully-worked example restaurant (“Karahi Point”) — log in, click through the console and apps, then create your real company the same way.

Adding it to an ERP you already run

No new server, no data migration of your existing modules — three steps.
1

Update your build to a version that includes the restaurant module, and roll it out the way you normally deploy.

2

Run the new migrations. They only add restaurant tables and links to your existing inventory & customers — nothing existing is altered.

3

Switch the Restaurant feature on for your company. Within a minute the Restaurant section appears, reusing your customers, inventory and chart of accounts.

Before you open — first-run setup

A new restaurant needs a handful of things configured so bills settle and cost correctly. Most is point-and-click in the web console.
One-time links
  • ✓Accounting accounts — Cash, Inventory, Sales, Sales Tax, Cost of Goods Sold — then map them to the restaurant. So bills reach the ledger.
  • ✓Kitchen store & ingredients — stocked in whole units (grams / ml / pieces). The costing engine works in base units.
  • ✓Tax rate — e.g. 16% for PRA. Applied on every bill.
In the web console
  • ✓Menu — categories, items, prices, photos, kitchen station, modifiers.
  • ✓Floor — draw areas and drag your tables into place.
  • ✓Recipes — ingredients per dish. This turns each sale into a real food cost and stock deduction.
  • ✓Staff accounts — one per person; don't share the owner login.

Running it in production

What it takes to keep it healthy once it's live.

Health

Point your uptime monitor at /health/ready — green only when the database and cache are reachable, and it steps aside cleanly on restart.

Monitoring

Grafana ships in the stack with live metrics — order and settlement rates, error rates. Change its default password.

Backups

Your whole business is in Postgres. Scheduled backup & restore scripts are included — test a restore before you rely on it.

Updates

git pull → rebuild → migrate. Rolling restarts don't drop in-flight orders — the outbox design guarantees it.

Multi-branch

One server can host many companies or branches, each with isolated data and its own switched-on modules.

Security

Rotate the three secrets, serve over HTTPS, restrict the platform super-admin, and give each staff member their own login.
